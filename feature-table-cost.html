Feature table cost

Data-driven line paint moves from a per-vertex attribute into a 96-byte record shared by every vertex of the feature. Constant properties stay uniforms. The record is a win once enough vertices share it, and a tax on short features and on any frame that changes the set of loaded tiles.

Static model from struct sizes and the miter polyline generator on feature-tables versus main. Metal, Vulkan, and WebGPU only. OpenGL still writes per-vertex attributes. One float property is 8 bytes on main; color alone is 16; all six simple-line properties are 56. A miter join emits 2 vertices per input coordinate, so a two-point line is 4 vertices. Branch GPU bytes per feature are 4·V + 96, assuming the record is fetched once per feature per frame.

Style filtering

A layer filter runs once per source feature, on main and on this branch, and rejected features are not stored. Zoom-only and constant paint collapse to uniforms, so a class split with a fixed width never builds a feature table. A feature expression still stores one 96-byte record per kept feature, including features that evaluate to the same value. Different filters are separate buckets, so exclusive class layers each tessellate and upload their own subset, and overlapping data-driven layers pay twice.

Filtering scales both sides with the features that survive. The ratio stays put while vertices per kept feature stay put. Keeping 10% of an unchanged mix is the same 0.80 ratio as keeping everything. Keeping long lines improves it. Keeping short lines with one varying float is the loss.

GPU bytes per vertex

Main’s cost is flat: the same paint payload is fetched for every vertex. The branch adds 4 bytes of index per vertex and spreads 96 bytes across the feature, so long lines get cheaper and a two-point line with one varying property gets more expensive. The record size does not grow with the number of properties.

What the 96 bytes contain

Every data-driven line layer allocates the full record as soon as one property varies. A simple line reads 56 bytes of it. Floor width and both pattern rects ride along as zeros.

The vertex shader loads the fields it uses. The allocation and the upload move all 96.

Navigation versus zooming

Screen model: one data-driven line layer, 24 tiles, 1,000 features per tile, 40 vertices per feature. Multiply by the number of data-driven line layers. A casing layer and a stroke layer each keep their own index and their own record, because each layer has its own tweaker.

Navigation — stable tiles

The feature buffer is built when the tile set settles, then left alone. Pan and a slow zoom that does not load or drop tiles do not repack or reupload it. Zoom still updates the per-drawable interpolation uniforms, which main already did.

Per frame the GPU reads the index plus each feature’s record. For this screen that is 5.9 MiB either way the properties are counted, against 7.3 MiB for one float and 51 MiB for six properties on main.

CPU added per frame is a walk of the layer’s drawables to confirm the bucket order. A feature-state change rewrites one slot, then the next frame uploads the whole layer buffer.

Zooming — tiles arriving steadily

Any change to the set or order of buckets concatenates every visible tile’s records and uploads them. Records for tiles that did not change are copied from the cache, so expressions are not evaluated again. The upload is the whole layer.

The buffer is allocated to the exact byte count. Each time zooming in adds features, that is a new GPU allocation plus the full copy. Zooming out updates in place until the live size drops below half, then allocates a smaller buffer.

Replacing one of the 24 tiles uploads 2.35 MiB. Main uploads only the new tile: 0.31 MiB for one float, 2.14 MiB for six properties. Loading all 24 at once is 5.9 MiB on the branch versus 7.3 MiB or 51 MiB on main.

CPU at tile build

Expression evaluation is unchanged: once per feature for a zoom-constant property, twice for a zoom composite. The vertex loops go away. Main copies the paint value onto every vertex. The branch writes one float4 per property and fills the index with a single value.

 Pattern layers also drop the per-vertex zoom-in and zoom-out rect vectors (16 bytes per vertex on main). Pattern direction changes republish one rect per feature, then take the same full-layer upload.

Where this lands. A navigation view with road lines of a few dozen vertices, or a route of hundreds, reads less GPU memory every frame and builds tiles with less CPU traffic. The cost shows up on short features that vary a single property, and on a zoom that keeps swapping tiles: the feature buffer is layer-global, exact-fit, and reuploaded in full whenever the tile set changes.

Filtering helps the branch when the survivors are long, and it hurts when a single varying property is left on short lines. Splitting classes into constant-paint layers turns the feature table off. Splitting them into data-driven layers keeps the same total bytes and multiplies the buffers that a zoom reuploads. A style whose line properties are all constants does not allocate the index or the record.
