Feature table cost

Data-driven line paint moves from a per-vertex attribute into a record shared by every vertex of the feature. The record holds only the properties that vary per feature, packed as floats with no padding. Constant and zoom-only properties stay uniforms. A per-vertex index still costs 4 bytes, so long lines approach that floor, and a zoom that swaps tiles still reuploads the whole layer.

Model from the packed feature layout and the miter polyline generator on feature-tables versus main. Metal, Vulkan, and WebGPU only. OpenGL still writes per-vertex attributes. One float is 8 bytes on both sides; color is 16; all six simple-line properties are 56. The old fixed 96-byte record is gone. A miter join emits 2 vertices per input coordinate, so a two-point line is 4 vertices. Branch GPU bytes per feature are 4·V + R.

Style filtering

A layer filter runs once per source feature, on main and on this branch, and rejected features are not stored. Zoom-only and constant paint collapse to uniforms, so a class split with a fixed width never builds a feature table. A feature expression still stores one record per kept feature, including features that evaluate to the same value. Different filters are separate buckets, so exclusive class layers each tessellate and upload their own subset, and overlapping data-driven layers pay twice.

Filtering still scales both sides with the features that survive, and the ratio stays put while vertices per kept feature stay put. With the tight record, a short line that varies one float is cheaper on the GPU than main. The zoom upload is the case that can still lose, because the whole layer moves when one tile arrives.

GPU bytes per vertex

Main’s cost is flat: the same paint payload is fetched for every vertex. The branch adds 4 bytes of index per vertex and one record per feature. With a single float the record is 8 bytes, so a two-point line is already cheaper. With all six properties the record is 56 bytes, the same payload main repeats on every vertex.

What goes in the record

Each data-driven property contributes its zoom pair and nothing else. Fields are concatenated in catalog order. A simple line that varies only width stores 8 bytes. The same line varying color and width stores 24. All six simple-line properties store 56, which is the old fixed record with floor width and both pattern rects removed.

Navigation versus zooming

Screen model: one data-driven line layer, 24 tiles, 1,000 features per tile, 40 vertices per feature. Multiply by the number of data-driven line layers. A casing layer and a stroke layer each keep their own index and their own record, because each layer has its own tweaker.

Navigation — stable tiles

The feature buffer is built when the tile set settles, then left alone. Pan and a slow zoom that does not load or drop tiles do not repack or reupload it. Zoom still updates the per-drawable interpolation uniforms, which main already did.

Per frame the GPU reads the index plus each feature’s record. For this screen that is 3.8 MiB with one float and 4.9 MiB with six properties, against 7.3 MiB and 51 MiB on main.

CPU added per frame is a walk of the layer’s drawables to confirm the bucket order. A feature-state change rewrites one slot, then the next frame uploads the whole layer buffer.

Zooming — tiles arriving steadily

Any change to the set or order of buckets concatenates every visible tile’s records and uploads them. Records for tiles that did not change are copied from the cache, so expressions are not evaluated again. The upload is the whole layer.

The buffer is allocated to the exact byte count. Each time zooming in adds features, that is a new GPU allocation plus the full copy. Zooming out updates in place until the live size drops below half, then allocates a smaller buffer.

Replacing one of the 24 tiles uploads 0.34 MiB for one float and 1.43 MiB for six properties. Main uploads only the new tile: 0.31 MiB and 2.14 MiB. Loading all 24 at once is 3.8 MiB or 4.9 MiB on the branch, versus 7.3 MiB or 51 MiB on main.

CPU at tile build

Expression evaluation is unchanged: once per feature for a zoom-constant property, twice for a zoom composite. The vertex loops go away. Main copies the paint value onto every vertex. The branch writes one float4 per property and fills the index with a single value, then packs the tight record when the layer is drawn.

 The 176 KB and 256 KB figures are the float4 value tables plus the index, written while the bucket is built. Packing copies 8 or 56 bytes per feature into the GPU buffer. Pattern layers also drop the per-vertex zoom-in and zoom-out rect vectors (16 bytes per vertex on main).

Where this lands. Dropping the unused fields removes the tax on a single varying property. A two-point line with one float is cheaper on the GPU than main, and a road of 40 vertices is about half the paint traffic. The remaining costs are the 4-byte index, which dominates long lines, and the layer-global buffer, which a zoom still reuploads in full.

That reupload is now a near tie for one float at 40 vertices, and a win when several properties vary or the lines are long. Short lines with one float still lose on the zoom upload, because 24 tiles of records outweigh one new tile’s vertex paint. Constant-paint class layers still allocate nothing.
